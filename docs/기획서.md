# Rehearview (리허뷰) 기획서

음성 모의면접 웹 서비스

작성일 2026-10-28 / 상태 초안

이 문서는 구현 전에 쓴 초기 기획서다. 구현하면서 일부가 바뀌었다(예: 면접 유형은 "종합"으로 단순화). 현재 동작은 각 저장소의 README와 코드를 기준으로 한다.

서비스명 Rehearview는 rehearsal(리허설)과 interview(면접)의 합성어이며, 한글 표기는 "리허뷰"로 고정한다. 공개 범위는 일반 공개다.

## 1. 배경과 문제

취업 준비생이 면접 말하기를 혼자 연습하기 어렵다. 사람과 하는 모의면접은 시간과 비용이 들고, 기존 AI 면접 서비스는 대체로 유료이거나 내 서류(이력서, 자기소개서)를 반영하지 못한 일반 질문만 던진다.

개발자 본인이 지원 서류를 기반으로 질문을 받고 음성으로 답하는 로컬 도구를 직접 만들어 면접 준비에 써 왔다(Node 서버 + 브라우저 음성 인식/합성). 이 도구를 누구나 접속해 쓰는 웹 서비스로 확장한다.

## 2. 목표

- 서류를 올리면 그 내용에서 질문이 나오고, 음성으로 답하고, 꼬리질문과 채점 리포트까지 받는 면접 연습 서비스를 완성한다.
- 로그인 후 면접 기록을 저장하고 다시 볼 수 있다.
- 외부 비용 없이 운영 가능한 구조(무료 LLM 티어 + 무료 호스팅)로 배포한다.
- 포트폴리오 관점 목표: 인증, DB 설계, 외부 API 연동과 장애 대응, 배포까지 한 프로젝트에서 보여 준다.

## 3. 대상 사용자

- 직군 제한 없이 서류를 준비한 모든 취업 준비생과 이직자 (사무, 영업, 마케팅, 서비스, 기술, 의료, 교육, 공공 등).
- 첫 사용자는 개발자 본인이며, 초기 검증은 본인 서류로 하되 다른 직군 샘플로도 반드시 확인한다.

## 4. 핵심 기능 (MVP)

1. 회원가입/로그인: 이메일+비밀번호(로컬) 로그인과 소셜 로그인(GitHub, 네이버, 카카오, 구글). 로컬 가입은 이메일 인증 완료 후 로그인 가능하고, 비밀번호 재설정도 인증 메일로 처리한다. 같은 이메일의 로컬/소셜 계정은 양쪽 모두 이메일이 인증된 경우에만 자동 연결한다.
2. 서류 업로드: PDF, DOCX를 브라우저에서 텍스트로 추출 (서버로는 텍스트만 전송)
3. 면접 설정: 회사, 직군(목록 선택 + 직접 입력), 직무, 유형(직무역량/인성/임원/컬처핏), 강도(순한맛/보통/매운맛). 직군은 특정 분야에 고정하지 않고, 서류와 직무 입력만으로 질문이 생성되게 한다.
4. 면접 진행: 질문을 음성으로 읽어 주고, 사용자는 음성으로 답하며(인식 결과는 수정 가능), 답변에 맞는 꼬리질문이 이어짐
5. 리포트: 6축 채점과 문장별 피드백 생성, 저장
6. 내 면접 기록 목록과 상세 보기

### MVP 제외 (향후)

- 영상/표정 분석, 서버 STT, 팀/공유 기능, 결제, 모바일 앱, 다국어

## 5. 사용자 흐름

로그인 → 서류 업로드 → 면접 설정 → 면접 진행(질문 → 답변 → 꼬리질문 반복) → 종료 → 리포트 생성 → 기록 저장 → 기록 목록에서 재열람

## 6. 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 프론트엔드 (`frontend/`) | Next.js 15 (App Router, TypeScript) | 화면과 브라우저 쪽 처리(음성, 서류 텍스트 추출) 담당. 포트폴리오 사이트와 동일 스택 |
| 스타일 | Tailwind CSS | 빠른 UI 구성 |
| 백엔드 (`backend/`) | Express 5 + TypeScript, 별도 프로젝트로 분리 | 인증, LLM 호출, DB 접근 담당. 프론트·백엔드 분리 구조를 포트폴리오에서 보여 주기 위함 |
| DB | PostgreSQL + Prisma 7 (`@prisma/adapter-pg`) | 관계형 모델링, 타입 안전 쿼리 |
| 인증 | 백엔드에서 직접 구현: 이메일+비밀번호(로컬) + OAuth(GitHub, Naver, Kakao, Google) | Auth.js는 Next.js용이라 사용하지 않음. 라이브러리는 Passport 계열을 후보로 두되 제공사별 패키지의 유지 상태를 구현 전에 확인. 비밀번호는 해시 저장. 세션은 httpOnly 쿠키 방식으로 하고 세부(서버 세션 vs JWT)는 구현 시 확정 |
| 음성 | Web Speech API (인식/합성) | 서버 STT 비용 없음. 인식은 Chrome에서 확인됐고 Edge는 network 오류가 나는 경우가 확인됨(2026-10-28). 인식이 안 되면 글자 입력으로 대체. 브라우저·OS에 따라 인식 품질이 달라 안정성이 필요해지면 서버 STT(예: 오디오 녹음 후 Gemini 등)로 교체 검토 |
| LLM | Gemini 무료 API 기본, OpenAI 호환 폴백 | 비용 0, 한도 초과 대비 |
| 메일 발송 | 무료 티어가 있는 트랜잭션 메일 서비스 (Resend 등, 후보 비교 필요) | 인증·재설정 메일. 월/일 발송 한도와 발신 도메인 설정(SPF, DKIM)을 구현 전에 확인 |
| 배포 | 프론트 Vercel, 백엔드 별도 무료 호스팅(후보 조사 필요), 무료 Postgres (Neon 또는 Supabase) | 무료 티어로 운영. 백엔드 호스팅은 슬립·시간 제한 같은 무료 티어 조건을 확인한 뒤 선정 |

## 7. 아키텍처

저장소는 모노레포이며 `frontend/`(Next.js)와 `backend/`(Express)를 각각 실행·배포한다. 브라우저가 음성 인식/합성과 서류 텍스트 추출을 담당하고, 백엔드가 인증, LLM 호출, DB 저장을 담당한다.

프론트와 백엔드의 도메인이 다르면 쿠키가 제3자 쿠키로 취급되어 로그인 유지가 막힐 수 있다. 이를 피하기 위해 Next.js의 rewrites로 `/api/*` 요청을 백엔드로 프록시해 브라우저에서는 같은 출처로 보이게 하는 방안을 기본으로 하고, 구현 시 실제 동작을 확인한다.

프론트엔드는 App Router의 라우트 그룹으로 비회원과 회원 영역을 나눈다.
- `app/(guest)/`: 랜딩, 로그인, 가입, 비밀번호 찾기·재설정, 아이디 찾기, 이메일 인증. 로그인·가입 화면은 이미 로그인한 사용자를 회원 영역으로 보낸다.
- `app/(member)/`: 면접 목록(`/interviews`), 새 면접(`/interviews/new`) 등. 레이아웃에서 서버가 쿠키를 백엔드(`/auth/me`)로 검증하고, 로그인이 없으면 `/login`으로 보낸다.
- 공용 코드는 `components/{common,landing,auth,member}`, 서버 전용 로그인 확인은 `lib/server/session.ts`, 경로 상수는 `lib/routes.ts`에 둔다.

LLM 호출은 단일 모듈로 추상화한다. 제공사별 `baseURL`, 모델명, 키를 설정으로 받고, 기본 제공사가 한도 초과나 503을 반환하면 지정한 폴백 제공사로 재시도한다. 기존 도구에서 Gemini 무료 티어가 분당 5회 한도와 과부하 503이 잦았던 경험에 따른 설계다.

## 8. 데이터 모델 (초안)

- User: id, email, emailVerified(인증 시각, 미인증이면 null), passwordHash(로컬 가입자만, 소셜 전용이면 null), createdAt
- VerificationToken: id, userId, tokenHash, purpose(이메일 인증/비밀번호 재설정), expiresAt, usedAt (토큰 원문은 저장하지 않고 해시만 저장, 1회용)
- Account: id, userId, provider, providerAccountId (한 User에 여러 소셜 연결 가능)
- Interview: id, userId, company, role, type, intensity, status, createdAt
- Turn: id, interviewId, order, question, answer, kind(기본/꼬리)
- Report: id, interviewId, scores(6축 JSON), feedback, createdAt

서류 원문과 추출 텍스트는 DB에 저장하지 않는다(확정). 면접 진행 중에는 브라우저가 서류 텍스트를 메모리(또는 sessionStorage)에 들고 있다가 질문 생성 요청마다 서버에 함께 보내고, 서버는 이를 LLM 호출에만 쓰고 버린다. 서버 로그에는 요청 본문(서류, 답변)을 남기지 않는다.

저장하는 것은 면접 설정, 질문·답변 텍스트(Turn), 리포트뿐이다. 서류 원문이 없으므로 새로고침이나 탭을 닫으면 진행 중이던 면접은 서류를 다시 올려야 이어갈 수 있고, 완료된 면접의 기록과 리포트는 그대로 볼 수 있다. 리포트에 서류 문장을 인용하는 경우 그 인용문은 리포트에 포함되어 저장되므로, 삭제 기능 범위에 포함한다.

## 9. 개인정보와 보안

- 서류에는 개인정보가 들어 있다. 전송 전 전화번호, 이메일, 주소 패턴을 자동 마스킹한다.
- 무료 LLM 티어는 입력이 제공사의 모델 개선에 쓰일 수 있다. 서류 업로드 화면에 이 사실을 고지하고 동의를 받는다.
- API 키는 서버 환경변수로만 보관하고 클라이언트에 노출하지 않는다.
- 사용자별 호출 횟수 제한(일일 면접 수)을 둔다.
- 사용자는 본인 기록을 삭제할 수 있다.

## 10. 열린 결정 사항

1. 서류 원문 저장 여부: 저장하지 않음으로 확정 (2026-10-28). 이에 따라 진행 중 면접 이어하기는 지원하지 않는다.
2. 인증 방식: 확정 (2026-10-28). 로컬(이메일+비밀번호) + 소셜 4종(GitHub, 네이버, 카카오, 구글). 세부 결정 확정: 이메일 인증을 도입하고, 로컬/소셜 계정은 양쪽 이메일이 인증된 경우에만 자동 연결한다. 남은 세부 결정: 메일 발송 서비스 선정, 인증 토큰 유효 시간.
3. 폴백 LLM 제공사: 잠정 선정 (2026-10-28, mnfst/awesome-free-llm-apis 기준). 순서는 Gemini(기본) → Groq(gpt-oss-120b, 분당 30회·일 1,000회, 응답 빠름) → Cloudflare Workers AI(일 10,000 Neurons 공유, 초과 시 과금 없이 요청 실패). 비상용으로 Mistral(무료 입력이 학습에 쓰이므로 옵트아웃 설정 필수). 제외: Cohere(비상업 전용), OpenRouter 무료(전체 일 50회, 무료 제공사가 프롬프트를 학습에 쓸 수 있음), OVHcloud 익명(IP당 분당 2회라 서버 한 곳에서 쓰기엔 부족), Z AI(서버가 중국), Aion Labs(일 2만 토큰). 공개 전 각 제공사의 약관과 데이터 사용 정책을 원문에서 직접 확인하고, 한국어 면접 질문 품질을 실제 서류로 비교 테스트한 뒤 확정한다.
4. 서비스 공개 범위: 일반 공개로 확정 (2026-10-28). 이에 따라 개인정보처리방침과 이용약관 페이지를 MVP에 포함하고, 무료 LLM 한도 보호를 위해 가입 필수와 일일 면접 횟수 제한을 둔다.
5. 도메인과 상표: 도메인(rehearview.com 등)은 추후 구매하기로 함. RDAP 조회상 미등록으로 보이나 구매 시점에 재확인 필요. 상표는 키프리스 검색 전. 구매 전까지는 다음과 같이 진행한다.
   - 개발: 인증·재설정 메일은 실제 발송 없이 서버 콘솔에 링크를 출력하는 개발용 모드로 구현하고, 메일 발송 모듈은 인터페이스만 맞춰 둔다.
   - 소셜 로그인: 콜백 URL은 localhost와 Vercel 기본 주소(*.vercel.app)로 등록하고, 도메인 구매 후 각 콘솔에서 추가한다. 일부 제공사(특히 네이버, 카카오)는 서비스 URL 검수가 있어 도메인 확정 후 재등록이 필요할 수 있다.
   - 공개 전 필수: 도메인 구매, 발신 도메인 인증(SPF, DKIM), 메일 서비스 연결. 이것이 끝나기 전에는 일반 공개를 하지 않는다.

## 11. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 무료 LLM 한도 초과, 503 | 폴백 제공사, 재시도 후 사용자에게 대기 안내, 일일 제한 |
| Web Speech 미지원 브라우저 | 지원 브라우저 안내, 텍스트 입력 대체 모드 |
| LLM이 서류에 없는 내용을 지어냄 | 프롬프트에 서류 근거 제약, 리포트에 근거 문장 표시 |
| 직군별 질문 품질 편차 (개발 외 직군은 검증 부족) | 직군별 샘플 서류(사무, 영업, 서비스, 의료 등)로 질문 품질 점검, 프롬프트를 직군 비종속으로 작성, 사용자 피드백(질문 평가) 수집 |
| 서류 형식 다양성 (표, 이미지 중심 서류) | 텍스트 추출 실패 시 직접 붙여넣기 입력 제공 |
| 첫 턴에 면접관 역할 이탈 | 첫 질문 고정 문장, 매 턴 역할 재주입 (기존 도구 노하우 이식) |
| 개인정보 이슈 | 9절 조치, 최소 수집 |
| 소셜 로그인 앱 등록·심사 (특히 네이버, 카카오의 이메일 등 동의항목 권한) | 개발 단계는 테스트 계정으로 진행, 공개 전 각 개발자 콘솔에서 앱 등록과 동의항목 신청. 이메일을 못 받는 경우를 대비해 이메일 없는 소셜 계정도 가입되게 설계 |
| 로컬 로그인의 무차별 대입, 계정 탈취 | 비밀번호 해시, 로그인 시도 횟수 제한, 소셜 계정 연결은 인증된 이메일만 |
| 소셜 제공사가 이메일 인증 여부를 주지 않거나 불확실 (제공사별 차이) | 인증 여부가 확실한 경우에만 자동 연결, 불확실하면 연결하지 않고 별도 계정으로 두거나 로그인 후 사용자가 설정에서 직접 연결 |
| 메일 발송 한도·스팸함 분류 | 재전송 횟수 제한, 발신 도메인 인증 설정, 인증 안내 화면에 스팸함 확인 문구 |

## 12. 일정 (약 4주, 목표)

- 1주: 프로젝트 기반(모노레포 구성, DB 스키마, LLM 모듈과 폴백), 인증 일부(로컬 가입/로그인), 서류 업로드와 텍스트 추출. 인증을 직접 구현하므로 소셜 4종과 이메일 인증은 2~3주차로 나눠 진행하고 전체 일정이 늘어날 수 있다.
- 2주: 면접 진행 화면(음성 인식/합성, 질문·꼬리질문 흐름), 세션 저장
- 3주: 리포트 생성과 기록 목록/상세, 호출 제한
- 4주: 배포(임시 주소), 안내 문구와 README, 오류 처리 다듬기, 데모 데이터
- 공개 전: 도메인 구매 후 메일 발송 연결과 소셜 로그인 콜백 재등록, 이후 일반 공개 (도메인 구매 시점에 따라 일정이 달라짐)

## 13. 성공 기준

- 로그인부터 리포트 저장까지 배포 URL에서 끊김 없이 동작한다.
- 기본 LLM 장애 상황에서 폴백으로 면접이 이어진다.
- README에 문제 정의, 아키텍처 그림, 트러블슈팅 기록이 있다.
